评测程序退出 0 只代表报告成功生成，不代表业务通过。随后提出四个假设：输入缺失、中文匹配失效、分块/过滤/来源损坏、缓存不随知识库变化。以下探针调用真实模块，不替换检索器、不改源码；人工夹具都位于临时目录。

- 缺失文档：直接比较文件名前缀集合与索引 doc_id 集合。
- 中文匹配：缩减为一篇含退款说明的文档和一个自然中文退款问句；英文词匹配作对照。
- 丢尾段：缩减到 301 字正文，末字标记；300 字对照通过，301/600/601 字失败。
- 过滤顺序：两份文档分别显式适用 S01/S02，请求 S02 的 top-1，有符合条件的文档仍返回空。

清洁导出依然失败，排除了“只有工作树旧缓存才导致现象”；英文 BM25 对照通过，排除了“BM25 完全无法评分”。未尝试修补算法，因本轮范围为诊断；不宣称获得修复后的绿灯证据。

## 5. 启动诊断时的第二关与第三关边界

以下保留诊断当时的建议；后续用户已确认的范围收敛见第8节。

第二关优先修复可共享的文档摄取、索引生命周期、检索质量、适用性、原文来源，以及能证明这些能力的诊断记录。沿用 Python/FastAPI/SQLite 与现有 BM25，不因当前低分立即更换整套架构、引入向量服务或付费 reranker。

默认工程选择：严格 UTF-8 加针对实际 GBK 的回退；HTML 可见正文解析；保留原文与检索文本的映射；先用确定性的中文词项方案修复现有词法检索，通过实际变体题再判断是否需要更复杂方法。分词库、chunk 长度、overlap 等可逆细节由小样本对照决定，不需要重开规则访谈。重建后重启服务沿用第一关约定，不新增热更新要求。

全量评测同时暴露下列相邻问题，已保存响应和 sample-traces，但本轮不以源代码阅读代替逐项最小根因实验：

- 退款政策、员工迟到问句返回全量营业额；“现在营业时间”被误当销售日期问题。
- 版本题0/3、文档题0/8；来源错位会污染后续引用，但其余回答层错误不能都归结于来源。
- 追问失败；代码中 Service 获取 history 后未传给 planner.plan（service.py:157-159）；SessionStore 用一个全局列表并忽略 session_id（sessions.py:15-28）。后者尚未执行专门跨会话实验，本轮只列代码风险。
- S02 删除请求没有正确拒绝，而是返回文档答案；评测未出现 metrics_unchanged 失败，不能据此宣称数据库遭到删除，也不能据此宣称完整安全验收已通过。
- answerer.py:77 的候选排序方向、上下文截断及异常诊断还需独立反馈环，不作为本轮已验证修复结论。

这些问题在检索修复后必须再跑完整评测并分流：属于检索/文档证据共享层的继续纳入第二关，属于混合编排、会话、前端聊天和真实模型接入的进入第三关。不能把第二关理解成“15道检索题通过就结束”，也不在本次启动诊断中悄然扩成第三关完整实施。
