## 共用交付规则

以下条款也包含在各任务的交付要求中；发布时保留，避免执行者只读一张 Issue 丢失边界。

1. 从任务书、契约、实际 KB 与诊断出发，不把公开题答案、商品/门店/文档编号或35篇计数写死在产品逻辑中。
2. 每个实际缺陷先建立真实调用路径的失败回归并保存输出，再修复并保留绿灯；阶段性提交必须遵循仓库格式。发布/执行获授权后才进行这些提交。本次诊断已有的红灯可作为起点，但需在执行基线上重现。
3. 按任务书补 `DEBUG_LOG.md`：现象、真实提出/排除的假设、实验关键输出、根因文件行号、修复提交、回归测试及修复前红灯；不得补写未发生的诊断过程。
4. 不用固定命中的检索替身验收 RAG；不改公开题库或评分器；不将 xfail、跳过、弱化断言当修复。
5. 保留第一关指标/数据题结果及既有未提交材料。修改共享代码时补跑受影响验证；最终整体验收覆盖已有看板。
6. SPEC EXECUTION RECEIPT 按验收项对应命令/输出/实际结果，列出执行基线与交付提交、剩余风险、工作树/分支/自己启动的 PID 和端口、需要保留的产物。后续获准执行时沿用主会话独立核验、决定合并、核对 Issue 状态和归档；执行会话负责修正、同步 main、补验与获准后的清理。PR 自动可合并不等于集成验收通过。
7. 无模型验收必须明确移除 LLM 配置，不能加载 `.env.live`。业务代码修复以外不顺手部署、调用付费模型或开始第三关。
