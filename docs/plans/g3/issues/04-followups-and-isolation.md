## What to build

同一会话中，运营可以问“那 7 月呢”“这两个月差多少”“当时呢”或继续问同一事件。系统继承必要上下文，重新查询和检索；换主题或新建对话后不误用旧条件。不同会话交错请求也不能串线。

## Acceptance criteria

- [ ] 原 T01/T02/T03 与 V03 的完整多轮顺序成为验收场景，逐轮保存请求/响应/trace；不能用改写成完整问句的单轮通过替代追问通过。受控模型与真实业务链先验证，真实模型语义结果按授权另验。
- [ ] 明确区分原始问题、解析后的上下文和本轮查询/检索条件；追问可继承指标、对象及相关时间，用户明确指定的新值优先。跨月比较包含两个独立查询及代码计算，历史追问重新选择当时有效版本，不直接复述旧答案或复用旧证据。
- [ ] 新主题清除不再适用的旧条件；澄清后的补充能继续原问题，失败/refusal 不把错误事实写成下一轮依据。缺少上下文时澄清，不默默查询全量。用自然变体检验，不靠固定短句表作为唯一语义入口。
- [ ] 两个不同 session_id 交错提问与追问，只使用各自历史；覆盖 API 并发及浏览器新建对话时旧请求迟到。相同会话的并发请求采用明确顺序或可解释拒绝，不能竞争写入错乱历史；不要求引入分布式队列。
- [ ] 内存历史具有明确的会话数与轮数上限；淘汰、服务重启或刷新导致上下文不可用时按产品说明重建会话或澄清，不能借用其他历史。没有 session_id 时也不落入共享匿名历史。无需跨设备/跨重启持久化。
- [ ] 前端连续消息、重试、新建对话与加载状态正确；聊天不会隐式继承看板筛选，改变看板筛选不会悄悄改写追问语义。用户主动附加的趋势引用按 G3-06 约定作为该条消息的上下文，跨票行为在 G3-05 验证。1280/1440/390 的实际浏览器操作有证据。
- [ ] 不同门店/商品/月份的替换输入验证继承规则仍成立；历史回答的文档仅作上下文，实际事实要从本轮适用证据获得。G3-01/02 单轮及前两关已验收行为保持，完整 trace 能重建上下文选择过程。
